# KeyFlow 代码结构

## 1. 总体目录

```text
keyflow/
├── src/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   ├── interfaces/
│   ├── container/
│   └── main.py
├── tests/
├── docs/
├── scripts/
├── docker/
├── pyproject.toml
├── README.md
├── .env.example
└── .env
```

---

## 2. 分层职责

### 2.1 `domain/`

只放纯业务核心，不依赖 FastAPI、Redis、SQLAlchemy。

建议结构：

```text
domain/
├── entities/
│   └── api_key.py
├── value_objects/
│   ├── key_status.py
│   └── provider.py
├── services/
│   ├── scheduler.py
│   ├── scorer.py
│   └── state_machine.py
├── repositories/
│   └── key_repository.py
└── exceptions/
    └── domain_exceptions.py
```

职责：

- 定义 `ApiKey`
- 定义 `KeyStatus`
- 定义评分与排序规则
- 定义状态机
- 定义仓储抽象协议

注意：

- `domain` 不应依赖插件私有余额/价格逻辑
- `v1` 评分以通用信号为主，不引入统一 `quota_score` 依赖

### 2.2 `application/`

负责用例编排，把接口请求转换成领域操作。

建议结构：

```text
application/
├── commands/
│   ├── create_key.py
│   ├── report_error.py
│   └── report_success.py
├── queries/
│   └── allocate_key.py
└── services/
    └── key_service.py
```

职责：

- 组织一次完整分配流程
- 协调仓储、缓存、状态机、插件
- 作为接口层默认依赖入口

说明：

- `queries/` 和 `commands/` 体现 CQRS 目录边界
- `KeyService` 可作为当前阶段的应用服务入口

### 2.3 `infrastructure/`

放所有外部依赖实现。

建议结构：

```text
infrastructure/
├── db/
│   ├── models.py
│   ├── repository_impl.py
│   └── session.py
├── cache/
│   ├── redis_client.py
│   ├── key_cache.py
│   └── lua/
│       └── allocate.lua
├── config/
│   └── settings.py
├── plugins/
│   ├── base.py
│   └── providers/
└── logging/
    └── logger.py
```

职责：

- PostgreSQL 持久化
- Redis 高并发分配
- Lua 原子分配脚本
- provider 插件实现
- 配置与日志

### 2.4 `interfaces/`

只负责 HTTP 表达层。

建议结构：

```text
interfaces/
├── api/
│   ├── app.py
│   ├── deps.py
│   └── routes/
│       ├── allocate.py
│       ├── report.py
│       ├── admin.py
│       └── health.py
├── schemas/
│   ├── request.py
│   └── response.py
└── middleware/
    └── auth.py
```

职责：

- 暴露 API 路由
- 定义请求响应模型
- 处理鉴权和依赖注入

注意：

- 接口层不应直接实现调度算法
- 接口层只负责收参、校验、调用应用服务、返回结果

### 2.5 `container/`

负责依赖装配。

```text
container/
└── container.py
```

职责：

- 创建 settings
- 装配 repository / cache / plugins / service
- 为 `app.py` 和 worker 提供统一对象图

---

## 3. 模块依赖关系

```text
interfaces -> application -> domain
                    ↓
             infrastructure
```

依赖原则：

- 依赖只能向内
- `domain` 不依赖 `infrastructure`
- `interfaces` 不直接操作数据库或 Redis


## 5. 脚本与运行入口

### 5.1 `scripts/`

```text
scripts/
└── init_db.py
```

职责：

- 初始化数据库
- 承担一次性环境准备脚本

---

## 6. Docker 与部署文件

```text
docker/
├── Dockerfile
└── docker-compose.yml
```

职责：

- `Dockerfile`：应用基础镜像
- `docker-compose.yml`：本地联调最小运行栈

推荐本地依赖：

```text
api + redis + postgres
```

---

## 7. 测试结构

```text
tests/
├── test_domain.py
├── test_api.py
├── test_provider_plugins.py
└── fakes.py
```

测试建议按层划分：

- `domain`：评分、排序、状态机
- `application/api`：分配、回写、CRUD
- `infrastructure`：Redis Lua、仓储实现
- `plugins`：provider 适配行为

---

## 8. 代码结构对应的架构原则

这套结构对应以下统一口径：

```text
账户归核心，状态归核心，调度归核心；
插件封装 provider 差异；
Redis 承担高并发分配；
PostgreSQL 承担持久化与管理面；
interfaces 只做 HTTP 表达，application 负责编排，domain 负责规则。
```

---

## 9. 总结

这套代码结构的本质可以概括为：

```text
调度规则在 domain，
用例编排在 application，
高并发能力在 Redis，
持久化真相在 PostgreSQL，
供应商差异在插件，
对外表达在 FastAPI。
```
