# KeyFlow 调度算法

本文按当前实现说明 key 分配、评分、状态机和 worker 刷新逻辑。

当前推荐运行模式：

```env
KEYFLOW_RUNTIME_MODE=local
```

local 模式使用 SQLite WAL 和 SQLite 分配存储；dev 模式使用 PostgreSQL + Redis/Lua。

## 1. 核心目标

KeyFlow 的调度目标是：在指定 provider 或指定 model 下，选择一个当前可用、并发未超限、状态正常、评分最高的 key，并返回给上游业务。

一次分配返回：

```json
{
  "key_id": "...",
  "lease_id": "...",
  "provider": "...",
  "provider_model": "...",
  "credential": {}
}
```

上游必须保存 `key_id` 和 `lease_id`，请求结束后调用成功或失败上报接口。

## 2. 两种分配入口

### 2.1 按 provider 分配

接口：

```text
POST /api/internal/allocate-key
```

请求核心字段：

```json
{
  "provider": "openai",
  "model": "gpt-4o",
  "pool": "default",
  "lease_seconds": 2
}
```

流程：

1. 根据 provider 和 pool 获取候选 key。
2. 恢复已到期的 `rate_limited` / `cooldown` key。
3. 根据 model 过滤候选 key。
4. 对候选 key 评分和排序。
5. 通过分配存储申请 lease。
6. 二次确认 key 仍然可用。
7. 返回 credential、`key_id`、`lease_id`、`provider_model`。

### 2.2 按 model 分配

接口：

```text
POST /api/internal/allocate-by-model
```

请求核心字段：

```json
{
  "model": "gpt-4o",
  "pool": "default",
  "lease_seconds": 2
}
```

流程：

1. 根据 pool 获取所有候选 key。
2. 读取 `config/model_aliases.yaml`。
3. 将统一模型名映射到 provider 原生模型名。
4. 只保留支持该模型的 key。
5. 评分、排序、申请 lease。
6. 返回实际 provider 和 `provider_model`。

## 3. Pool 规则

当前支持：

- `default`
- `vip`

分配时的 pool 序列：

- 请求 `default`：只看 `default`。
- 请求 `vip`：先看 `vip`，没有可用 key 时再 fallback 到 `default`。

对应逻辑在：

```text
src/application/services/key_service.py
```

函数：

```text
_allocation_pool_sequence
```

## 4. 候选 key 过滤

候选 key 必须满足：

- provider 匹配，或按 model 分配时存在模型别名匹配。
- pool 符合分配规则。
- `ApiKey.is_available(now)` 返回 true。
- key 没有超过并发 lease 限制。
- key 的模型列表支持请求模型。
- key 没被管理禁用。
- key 没被上报禁用。
- key 没被上游可用性检查禁用。
- key 没有配额耗尽。
- key 不在未到期冷却中。

不可分配状态：

```text
pending
disabled_upstream
disabled_admin
disabled_report
exhausted
```

临时不可分配状态：

```text
rate_limited
cooldown
```

这两个状态只有在 `cooldown_until <= now` 后才会恢复为 `available`。

## 5. 评分规则

评分入口：

```text
src/domain/services/scorer.py
```

排序入口：

```text
src/domain/services/scheduler.py
```

评分公式核心项：

```text
score =
  capacity_weight * capacity_score
  + idle_weight * idle_score
  + success_weight * success_score
  - error_weight * error_penalty
  - rate_limit_weight * rate_limit_penalty
  - cooldown_weight * cooldown_penalty
  - freshness_penalty
```

### 5.1 capacity_score

来源：

- provider 插件的 `get_capacity_signal()`。
- 如果插件没有可靠容量信号，使用 `capacity_unknown_fallback`。

用途：

- 表示该 key 当前容量、额度或预算可用程度。
- 范围按 0 到 1 处理。

### 5.2 idle_score

来源：

- `last_used_at`

含义：

- 越久没用，分数越高。
- 从未使用过的 key 视为最高 idle。
- 超过 `ALLOCATE_IDLE_CAP_SECONDS` 后封顶。

### 5.3 success_score

来源：

- `success_count`
- `error_count`

含义：

- 成功率越高，分数越高。
- 没有历史记录时按 1.0 处理。

### 5.4 error_penalty

来源：

- `error_count`

含义：

- 错误越多，扣分越多。
- 到 `ALLOCATE_ERROR_CAP` 后封顶。

### 5.5 rate_limit_penalty

如果状态是 `rate_limited`，扣分。

实际未到期的 `rate_limited` key 会先被 `is_available()` 过滤掉；该项主要保留给边界状态评分。

### 5.6 cooldown_penalty

如果 `cooldown_until` 还没到，按剩余冷却时间扣分。

实际未到期的 `cooldown` key 会先被过滤掉。

### 5.7 freshness_penalty

来源：

- `last_refreshed_at`

含义：

- 最近刷新过的 key 不扣分。
- 过旧的 key 按 stale / very stale 两档扣分。
- 没刷新过的 key 按 very stale 扣分。

## 6. 排序和随机扰动

`KeyScheduler.rank_keys()` 会：

1. 跳过不可用 key。
2. 调用 `KeyScorer.score()`。
3. 给分数加一个可配置随机扰动 `ALLOCATE_JITTER`。
4. 按分数从高到低排序。

随机扰动用于避免大量请求总是打到同一个最高分 key。

## 7. Lease 和并发控制

分配不是只在内存里选一个 key，而是要申请 lease。

请求参数：

```json
{
  "lease_seconds": 2
}
```

含义：

- lease 表示这个 key 在一小段时间内被某个请求占用。
- key 的并发上限由 `max_concurrent_uses` 控制。
- 超过并发上限时，该 key 暂时不会被继续分配。

local 模式：

- 使用 SQLite 分配存储。
- 实现文件：`src/infrastructure/cache/sqlite_key_cache.py`。

dev 模式：

- 使用 Redis + Lua 原子分配。
- 实现文件：`src/infrastructure/cache/key_cache.py`。
- Lua 文件：`src/infrastructure/cache/lua/allocate.lua`、`release.lua`。
- 同时有 DB 兜底同步：`CompositeKeyCache`。

## 8. 上报驱动状态机

状态机文件：

```text
src/domain/services/state_machine.py
```

### 8.1 成功上报

接口：

```text
POST /api/internal/report-success
```

成功上报会：

- `success_count += 1`
- `quota_used += tokens_used`
- 更新 `last_used_at`
- 清零 `consecutive_error_count`
- 清零 `rate_limit_rounds`
- 释放 lease
- 通知 provider 插件 `mark_success`

### 8.2 失败上报

接口：

```text
POST /api/internal/report-error
```

失败上报会：

- 标准化 `error_type`
- `error_count += 1`
- 更新 `last_used_at`
- 记录 `last_report_error_type`
- 根据错误类型改变状态
- 释放 lease
- 通知 provider 插件 `mark_error`

### 8.3 致命凭证错误

以下错误会直接进入 `disabled_report`：

```text
invalid_api_key
unauthorized
forbidden
account_disabled
credential_revoked
oauth_refresh_failed
```

进入 `disabled_report` 后，需要人工处理或更新凭证。

### 8.4 限流错误

以下错误视为限流：

```text
rate_limit
too_many_requests
429
```

处理方式：

- `rate_limit_rounds += 1`
- 状态设为 `rate_limited`
- 设置 `cooldown_until`
- 冷却时长按退避配置递增

### 8.5 普通临时错误

其他错误会累积 `consecutive_error_count`。

达到 `REPORT_TRANSIENT_FAILURE_THRESHOLD` 后：

- 清零连续错误计数。
- `cooldown_failure_rounds += 1`。
- 如果冷却轮次达到 `REPORT_COOLDOWN_DISABLE_ROUNDS`，进入 `disabled_report`。
- 否则进入 `cooldown`，并设置 `cooldown_until`。

## 9. 后台 worker

入口：

```text
src/worker_main.py
```

循环实现：

```text
src/interfaces/workers/background.py
```

周期配置：

```env
BACKGROUND_TASK_INTERVAL_SECONDS=60
```

worker 做两件事：

1. `recover_cooldowns`
2. `refresh_keys`

### 9.1 recover_cooldowns

作用：

- 查询已经到期的 `rate_limited` / `cooldown` key。
- 如果 `cooldown_until <= now`，恢复为 `available`。
- 同步到分配存储。

### 9.2 refresh_keys

作用：

- 找到需要刷新的 key。
- 调 provider 插件检查凭证是否可用。
- 调 provider 插件获取容量信号。
- 同步支持模型列表。
- 根据刷新结果更新状态。
- 同步到分配存储。

刷新时会保护这些人工或上报禁用状态：

- `disabled_admin`
- 默认不覆盖 `disabled_report`

## 10. Pending 校验

新增 key 时不会直接变成完全可用，而是先进入：

```text
pending
```

创建流程会：

1. 准备和规范化 credential。
2. 检查 provider 插件是否 ready。
3. 检查重复 credential。
4. 调 provider 验证上游根地址可达。
5. 保存 key。
6. 同步到分配存储。
7. 异步调度 pending validation。

pending validation 会刷新该 key：

- OAuth 凭证会先做 freshness check 和 refresh。
- 检查 credential 可用性。
- 拉取模型列表。
- 读取容量信号。
- 根据结果改为 `available`、`disabled_upstream` 或 `exhausted`。

## 11. 模型别名与 provider_model

配置文件：

```text
config/model_aliases.yaml
```

示例：

```yaml
version: 1
models:
  gpt-4o:
    providers:
      openai:
        - gpt-4o
      openrouter:
        - openai/gpt-4o
```

请求 `model=gpt-4o` 时：

- 可以分配 openai 的 `gpt-4o`。
- 也可以分配 openrouter 的 `openai/gpt-4o`。
- 返回的 `provider_model` 是上游真正调用 provider 时要使用的模型名。

## 12. 管理状态

管理员可写状态有限：

```text
available
disabled_admin
```

管理禁用：

- 设置为 `disabled_admin`。
- 分配时永远跳过。
- worker 不会自动恢复。

从 `disabled_admin` 恢复到 `available` 时：

- 会重新做 provider 检查。
- 检查不通过可能进入 `disabled_upstream` 或 `exhausted`。

## 14. 排障判断

### 14.1 没有可用 key

常见原因：

- provider 没录入 key。
- pool 不匹配。
- 模型别名没配置。
- key 在 `pending`。
- key 在 `cooldown` 或 `rate_limited`。
- key 是 `disabled_admin`、`disabled_report`、`disabled_upstream` 或 `exhausted`。
- lease 并发达到 `max_concurrent_uses`。

### 14.2 key 一直 pending

查：

- provider 插件是否 ready。
- 凭证格式是否正确。
- 上游是否可达。
- worker 是否运行。
- `keyflow-api` 日志是否有 pending validation 异常。

### 14.3 local 模式分配异常

查：

- `.env` 里 `LOCAL_SQLITE_PATH` 是否正确。
- 容器是否挂载 `/data`。
- SQLite 文件所在目录是否可写。
- 磁盘是否满。

命令：

```bash
docker logs --tail 200 keyflow-api
docker inspect keyflow-api --format '{{json .Mounts}}'
df -h
```
