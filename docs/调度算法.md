# KeyFlow 调度算法

## 1. 目标

`v1` 的调度目标不是追求理论最优，而是保证：

- 可用
- 可控
- 可恢复
- 可并发安全

核心问题可以表述为：

```text
在指定 provider 下，从当前账户池里选出一个最适合且当前可用的凭证。
```

---

## 2. v1 设计原则

### 2.1 不做统一额度经济模型

`v1` 不把余额、价格、套餐、剩余额度作为核心统一评分输入。

原因：

- 不同 provider 的计费规则差异极大
- 部分凭证类型没有统一余额概念
- 这些逻辑已经约定保留在插件内部

### 2.2 核心只使用通用信号

核心评分只依赖以下通用字段：

- `last_used_at`
- `success_count`
- `error_count`
- `status`
- `cooldown_until`

### 2.3 插件负责 provider 特有判断

插件负责：

- 认证是否有效
- Cookie / Token 是否过期
- provider 特有额度或余额是否仍可用
- 指定 `model` 是否可被当前凭证支持

核心只使用插件返回的布尔结果：

```text
is_credential_available(...)
```

## 3. v1 核心评分公式

```text
score =
  w1 * idle_score
+ w2 * success_score
- w3 * error_penalty
- w4 * rate_limit_penalty
- w5 * cooldown_penalty
```

### 3.1 idle_score

```text
idle_score = min(idle_seconds / idle_cap_seconds, 1.0)
```

含义：

- 越久没被使用，得分越高
- 作用是避免某个 key 长期热点

### 3.2 success_score

```text
success_score = success_count / (success_count + error_count)
```

无历史请求时可默认按健康凭证处理。

### 3.3 error_penalty

```text
error_penalty = min(error_count / error_cap, 1.0)
```

普通错误越多，惩罚越高。

### 3.4 rate_limit_penalty

```text
rate_limit_penalty = 1.0 if status == RATE_LIMITED else 0.0
```

### 3.5 cooldown_penalty

```text
if cooldown_until > now:
    cooldown_penalty = 1.0
```

在冷却中时应不可选，或等价为极大惩罚。

### 3.6 随机扰动

为避免完全固定排序导致热点，可在最终分数中加入轻微抖动：

```text
final_score = score + random(0, ε)
```

## 5. 调度流程

### Step 1：获取 provider 下候选账户

候选账户来自核心数据库与 Redis 维护的 provider 集合。

### Step 2：按核心状态过滤

先过滤以下不可调度状态：

- `DISABLED`
- `EXHAUSTED`
- `COOLDOWN`

对 `RATE_LIMITED` 账户：

- 如果 cooldown 已结束，可恢复为可调度
- 如果仍在退避窗口内，则跳过

### Step 3：按 model 做辅助过滤

如果请求携带 `model`：

- 若本地 `supported_models` 已同步，可先做本地辅助过滤
- 再把 `model` 传给插件做真实可用性判断

### Step 4：插件可用性过滤

```text
if not plugin.is_credential_available(api_key, model):
    skip
```

### Step 5：计算 score

对剩余候选计算统一评分。

### Step 6：按分数排序

```text
按 final_score 从高到低排序
```

### Step 7：Redis + Lua 原子分配

Lua 脚本必须完成：

1. 校验 key 仍在候选集合内
2. 校验 key 当前状态仍可分配
3. 写入占用信息或租约信息
4. 返回分配结果

### Step 8：返回结果

若成功返回选中凭证；若没有可分配凭证，则返回 `no_available_key`。

## 6. 成功与失败回写

### 6.1 成功

```text
success_count += 1
quota_used += tokens_used
last_used_at = now
status = AVAILABLE
cooldown_until = None
```

### 6.2 普通错误

```text
error_count += 1
last_used_at = now
score 下降
```

### 6.3 rate_limit

```text
status = RATE_LIMITED
cooldown_until = now + backoff
```

推荐退避序列：

```text
1min -> 2min -> 5min -> 10min
```

### 6.4 quota_exhausted

```text
status = EXHAUSTED
```

说明：

这里的 `quota_exhausted` 是核心接受到的错误语义，不代表核心自己计算 provider 的余额模型。

---

## 7. 原子分配要求

仅“读取排序后第一个 key 并更新 `last_used_at`”是不够的。

真正满足并发安全，至少需要以下语义之一：

- 分配租约
- 占用标记
- 并发数控制
- 在 Lua 内完成校验与占用写入

目标是：

```text
同一时刻不要把同一个 key 重复分给多个并发请求。
```

---

## 8. 为什么 v1 先不做 quota_score

以下逻辑暂不进入统一核心评分：

- get_balance
- get_usage
- calculate_cost
- calculate_remaining_quota

原因不是这些信息没价值，而是它们不具备统一抽象前提。

如果后续确实要做 `v2` 成本感知调度，应该新增一层明确能力抽象，例如：

```text
QuotaAwareCapability
CostAwareCapability
ModelCapability
```

而不是把各 provider 的私有计费接口直接暴露给核心调度器。

---

## 9. v1 算法总结

```text
1. 获取 provider 下候选账户
2. 过滤核心不可用状态
3. 按 model 做本地辅助过滤
4. 调用插件判断凭证是否当前可用
5. 计算 idle/success/error/rate_limit/cooldown 统一分数
6. 加入轻微扰动后排序
7. 用 Redis + Lua 原子分配
8. 返回结果
9. 根据 success/error 更新核心状态
```

## 10. 未来扩展

以下能力属于后续版本扩展项：

- 统一额度感知调度

---

## 11. 总结

`KeyFlow` 的 `v1` 调度本质是：

```text
状态驱动调度 + 通用评分排序 + 插件可用性过滤 + Redis 原子分配
```
