# KeyFlow 调度算法

## 1. 目标

`v1` 的调度目标不是追求理论最优，而是保证：

- 可用
- 可控
- 可恢复
- 可并发安全

核心问题可以表述为：

```text
在指定 provider 下，从当前账户池里选出一个最适合且当前可用的凭证。
```

---

## 2. v1 设计原则

### 2.1 不做统一额度经济模型

`v1` 不把余额、价格、套餐、剩余额度原始字段直接作为核心统一评分输入。

原因：

- 不同 provider 的计费规则差异极大
- 部分凭证类型没有统一余额概念
- 这些逻辑已经约定保留在插件内部

### 2.2 核心使用通用健康信号 + 可选容量信号

核心健康评分依赖以下通用字段：

- `last_used_at`
- `success_count`
- `error_count`
- `status`
- `cooldown_until`

此外，核心还可以接收插件返回的**可选标准化容量信号**：

- `capacity_score in [0, 1]`
- `None` 表示 provider 无可靠额度数据
- `0.5` 作为默认中性回退值

### 2.3 插件负责 provider 特有判断

插件负责：

- 认证是否有效
- Cookie / Token 是否过期
- provider 特有额度或余额是否仍可用
- 指定 `model` 是否可被当前凭证支持

核心只使用插件返回的布尔结果：

```text
is_credential_available(...)
```

## 3. v1.1 核心评分公式

```text
score =
  w0 * capacity_score
+ w1 * idle_score
+ w2 * success_score
- w3 * error_penalty
- w4 * rate_limit_penalty
- w5 * cooldown_penalty
```

其中：

- `capacity_score` 是插件可选返回的运行时容量信号
- 如果插件没有提供该信号，则核心使用中性值 `0.5`
- 核心不直接理解 provider 原始余额/额度/价格字段

### 3.1 idle_score

```text
idle_score = min(idle_seconds / idle_cap_seconds, 1.0)
```

含义：

- 越久没被使用，得分越高
- 作用是避免某个 key 长期热点

### 3.2 success_score

```text
success_score = success_count / (success_count + error_count)
```

无历史请求时可默认按健康凭证处理。

### 3.3 error_penalty

```text
error_penalty = min(error_count / error_cap, 1.0)
```

普通错误越多，惩罚越高。

### 3.4 rate_limit_penalty

```text
rate_limit_penalty = 1.0 if status == RATE_LIMITED else 0.0
```

### 3.5 cooldown_penalty

```text
if cooldown_until > now:
    cooldown_penalty = 1.0
```

在冷却中时应不可选，或等价为极大惩罚。

### 3.6 随机扰动

为避免完全固定排序导致热点，可在最终分数中加入轻微抖动：

```text
final_score = score + random(0, ε)
```

### 3.7 capacity_score

```text
capacity_score ∈ [0, 1]
None -> fallback = 0.5
```

含义：

- `1.0`：容量非常充足
- `0.5`：未知容量，按中性处理
- `0.0`：容量极低或接近耗尽

来源：

- 由 provider 插件在内部用自己的额度模型换算
- 核心只消费归一化后的分数，不消费原始额度数据

## 5. 调度流程

### Step 1：获取 provider 下候选账户

候选账户来自核心数据库与 Redis 维护的 provider 集合。

### Step 2：按核心状态过滤

先过滤以下不可调度状态：

- `DISABLED`
- `EXHAUSTED`
- `COOLDOWN`

对 `RATE_LIMITED` 账户：

- 如果 cooldown 已结束，可恢复为可调度
- 如果仍在退避窗口内，则跳过

### Step 3：按 model 做辅助过滤

如果请求携带 `model`：

- 若本地 `supported_models` 已同步，可先做本地辅助过滤
- 再把 `model` 传给插件做真实可用性判断

### Step 4：插件可用性过滤

```text
if not plugin.is_credential_available(credential, model):
    skip
```

### Step 5：获取可选容量信号

```text
signal = plugin.get_capacity_signal(credential)
```

规则：

- provider 有可靠额度数据 -> 返回 `capacity_score`
- provider 无可靠额度数据 -> 返回 `None`
- 核心对 `None` 使用中性回退 `0.5`

### Step 6：计算 score

对剩余候选计算统一评分。

### Step 7：按分数排序

```text
按 final_score 从高到低排序
```

### Step 8：Redis + Lua 原子分配

Lua 脚本必须完成：

1. 校验 key 仍在候选集合内
2. 校验 key 当前状态仍可分配
3. 写入占用信息或租约信息
4. 返回分配结果

### Step 9：返回结果

若成功返回选中凭证；若没有可分配凭证，则返回 `no_available_key`。

## 6. 成功与失败回写

### 6.1 成功

```text
success_count += 1
quota_used += tokens_used
last_used_at = now
status = AVAILABLE
cooldown_until = None
```

### 6.2 普通错误

```text
error_count += 1
last_used_at = now
score 下降
```

### 6.3 rate_limit

```text
status = RATE_LIMITED
cooldown_until = now + backoff
```

推荐退避序列：

```text
1min -> 2min -> 5min -> 10min
```

### 6.4 quota_exhausted

```text
status = EXHAUSTED
```

说明：

这里的 `quota_exhausted` 是核心接受到的错误语义，不代表核心自己计算 provider 的余额模型。

---

## 7. 原子分配要求

仅“读取排序后第一个 key 并更新 `last_used_at`”是不够的。

真正满足并发安全，至少需要以下语义之一：

- 分配租约
- 占用标记
- 并发数控制
- 在 Lua 内完成校验与占用写入

目标是：

```text
同一时刻不要把同一个 key 重复分给多个并发请求。
```

---

## 8. 为什么容量信号不是统一额度模型

以下原始逻辑仍然**不直接**进入核心评分：

- get_balance
- get_usage
- calculate_cost
- calculate_remaining_quota

原因不是这些信息没价值，而是它们不具备统一抽象前提。

当前做法是折中方案：

- provider 自己理解原始额度模型
- provider 自己换算出标准化 `capacity_score`
- core 只消费 `0 ~ 1` 的统一信号

如果后续确实要做更强的成本感知调度，应该继续沿着能力抽象扩展，例如：

```text
QuotaAwareCapability
CostAwareCapability
ModelCapability
```

而不是把各 provider 的私有计费接口直接暴露给核心调度器。

---

## 9. v1.1 算法总结

```text
1. 获取 provider 下候选账户
2. 过滤核心不可用状态
3. 按 model 做本地辅助过滤
4. 调用插件判断凭证是否当前可用
5. 可选获取 provider 标准化容量信号
6. 计算 capacity/idle/success/error/rate_limit/cooldown 混合分数
7. 加入轻微扰动后排序
8. 用 Redis + Lua 原子分配
9. 返回结果
10. 根据 success/error 更新核心状态
```

## 11. 总结

`KeyFlow` 当前调度本质是：

```text
状态驱动调度 + 通用健康评分 + 可选容量信号 + 插件可用性过滤 + Redis 原子分配
```
