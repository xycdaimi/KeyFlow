# Provider Plugin Egress Design

- Date: 2026-04-16
- Status: Draft for review
- Scope: KeyFlow provider 插件的固定出网策略设计

## 1. 背景

当前 KeyFlow 部署通常以国内网络环境为主。
部分国外供应商在该环境下无法直接连通，如果主动检测、模型拉取、容量探测、OAuth 刷新等请求不走代理，会直接出现网站无法连接或上游不可达。

现有系统边界已经明确：

- `worker` 只负责周期调度
- `KeyService` 只负责调用 provider 统一接口并合并结果
- 实际供应商请求逻辑已经封装在 provider 插件内部

因此，这个问题不应通过扩展 worker 或 application 层解决，而应落在 provider 插件自身的网络访问策略上。

## 2. 目标

本设计只解决一个问题：

- 让部分 provider 插件在当前部署环境下能够稳定访问其供应商接口

本设计不解决以下问题：

- 通用代理池
- 动态路由选择
- provider 自动国内/国外识别
- 上游任务执行侧的复杂代理治理
- sticky IP、代理健康管理、出口调度

## 3. 设计结论

采用最小方案：

1. 每个 provider 插件内部直接写死自己的出网策略：`direct` 或 `proxy`
2. `.env` 只提供运行参数：固定代理地址、连接超时、读取超时、总超时
3. 该插件内所有对供应商的 HTTP 请求都遵循同一策略
4. `worker`、`KeyService`、状态机、分配逻辑全部无感知
5. 网络不可达统一归类为“网站无法连接 / 上游不可达”语义

## 4. 系统边界

### 4.1 归属

代理策略归属 provider 插件自身。

这意味着：

- 哪个 provider 需要代理，由插件代码决定
- 其他层不做任何判断
- 系统不引入独立的 egress 配置文件
- 系统不引入新的代理抽象层

### 4.2 非归属

以下模块不承担代理策略职责：

- `src/worker_main.py`
- `src/application/services/key_service.py`
- 分配流程
- 状态机
- 接口层

这些模块只看 provider 插件统一接口的返回值与异常结果。

## 5. 插件策略

### 5.1 固定策略

每个 provider 插件类内部声明固定网络策略：

- 国内 provider：`direct`
- 国外 provider：`proxy`

第一版不做：

- 自动探测直连是否可用
- 失败后 fallback 到代理
- 用配置文件覆盖 provider 的出网方式

原因是当前需求非常明确：

- 能直连的 provider 就直连
- 不能直连的 provider 就统一走固定代理

### 5.2 作用范围

该策略作用于插件内全部供应商 HTTP 请求，而不是仅作用于主动检测接口。

包括但不限于：

- `verify_upstream_root_reachable`
- `fetch_models`
- `is_credential_available`
- `get_capacity_signal`
- `prepare_credential`
- 插件内部其他访问供应商 API 的请求

这样可以保证同一个 provider 的全部外呼行为使用一致的网络路径，避免“某些接口能通、某些接口不通”的割裂状态。

## 6. 运行参数

运行参数从 `.env` 提供，而不是额外维护独立配置文件。

建议环境变量包括：

- `GLOBAL_HTTP_PROXY`
- `HTTP_CONNECT_TIMEOUT`
- `HTTP_READ_TIMEOUT`
- `HTTP_TOTAL_TIMEOUT`

职责划分如下：

- 插件代码决定 `direct` 还是 `proxy`
- `.env` 提供代理地址和超时数值

`.env` 不负责决定某个 provider 是否走代理。

## 7. 错误语义

如果 provider 插件在当前网络策略下请求供应商失败，并且失败原因属于网络不可达范畴，例如：

- DNS 失败
- 连接超时
- TLS 握手失败
- 代理不可用
- 网络不可达
- 连接被拒绝

则统一归类为：

- 网站无法连接
- 上游不可达

这类错误的语义是：

- 当前部署环境下，该 provider 在当前网络策略上不可达

而不是：

- 凭证失效
- 配额耗尽
- 账号异常

因此，网络不可达错误必须与凭证错误保持语义分离，避免把网络问题误判为 credential 无效。

## 8. 约束

### 8.1 超时必须存在

所有插件对供应商的 HTTP 请求都必须带超时控制。

原因：

- 某些不可达供应商会长时间卡住连接阶段
- 如果没有连接超时，worker 周期任务可能被阻塞
- 如果没有读取/总超时，代理异常时也可能拖死请求

### 8.2 不扩展到代理池

本设计只支持固定代理，不引入：

- 代理池
- 多代理切换
- 健康检查
- 动态选择策略

如果未来上游执行系统确实需要更复杂的出口治理，应放在上游执行侧实现，而不是先把 KeyFlow 扩展成代理平台。

## 9. 实施建议

第一阶段仅做以下改动：

1. 在需要代理的 provider 插件内写死网络策略
2. 复用现有插件内公共 HTTP 能力，按插件策略决定是否附带代理参数
3. 从 `.env` 读取固定代理地址与超时参数
4. 保持 `worker` 和 `KeyService` 不变
5. 保持现有 provider 统一接口不变

## 10. 验收标准

满足以下条件即可认为设计达标：

1. 国内 provider 在默认部署环境下继续直连工作
2. 国外 provider 在配置固定代理后可完成其插件内全部供应商请求
3. 代理未配置或代理不可用时，系统返回“网站无法连接 / 上游不可达”语义
4. 不因网络不可达将 credential 误判为失效
5. 不新增独立代理配置文件
6. 不修改 worker 与 application 层边界
