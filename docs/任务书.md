# KeyFlow 任务书

## 1. 项目定位

### 1.1 项目名称

- 项目名：`KeyFlow`
- 系统角色：`Provider Scoped Key Scheduling Service`

### 1.2 系统目标

构建一个面向账户池的凭证调度服务，为上游 `AI Router / Model-Forward` 提供稳定的内部获取 key 能力，既支持指定 `provider` 的 provider 内调度，也支持仅按 `model` 的跨 provider 选优分配。

### 1.3 在整体链路中的位置

```text
Client
  ↓
AI Router
  ↓
Model-Forward
  ↓
KeyFlow
  ↓
LLM Provider
```

---

## 2. 系统边界

### 2.1 KeyFlow 负责

- provider 内凭证调度
- 按模型跨 provider 选优分配
- 凭证核心状态管理
- 凭证账户池 CRUD
- 内部 `allocate/report` 接口
- cooldown 恢复等后台保障任务

### 2.2 KeyFlow 不负责

- provider fallback
- task routing
- 全局 model 选择
- 直接执行真实 LLM 请求

### 2.3 一条核心原则

`KeyFlow` 主要回答两个问题：

```text
1. 在指定 provider 下，当前应该分配哪一个可用凭证？
2. 在只指定 model 时，当前应该从哪个 provider 分配哪个可用凭证？
```

## 3. 架构原则

### 3.1 分层架构

```text
interfaces/        # FastAPI 接口层
application/       # 用例编排层
domain/            # 调度核心与状态机
infrastructure/    # Redis / PostgreSQL / 插件 / 配置
container/         # 依赖注入
```

### 3.2 CQRS 原则

命令侧：

- 创建凭证
- 更新凭证
- 删除凭证
- 上报成功
- 上报失败

查询侧：

- 获取可用凭证
- 查询账户池

### 3.3 真相源原则

- 账户真相源：核心数据库
- 正式状态真相源：核心状态机
- provider 差异判断：插件

---

## 4. 核心模型

### 4.1 账户语义

- `credential` 本身就是账户凭证载荷
- 一条记录代表一个可被调度的供应商凭证
- 不再引入 `display_name + secret` 双层账户模型

### 4.2 ApiKey 核心字段

```python
class ApiKey:
    id: str
    provider: str
    credential: dict[str, str]
    status: KeyStatus
    quota_used: int
    success_count: int
    error_count: int
    last_used_at: datetime | None
    cooldown_until: datetime | None
    supported_models: list[str]
```

说明：

- `quota_used` 仅作为核心统计字段保留
- 不在 `v1` 中要求统一的 `quota_total / balance / pricing` 核心模型
- 供应商特有的额度、价格、套餐逻辑保留在插件内部

### 4.3 核心状态机

```text
AVAILABLE
RATE_LIMITED
COOLDOWN
DISABLED
EXHAUSTED
```

### 4.4 状态迁移原则

- 成功：增加成功计数，更新 `last_used_at`
- 普通错误：增加错误计数，降低评分
- `rate_limit`：进入 `RATE_LIMITED / COOLDOWN`
- `quota_exhausted`：进入 `EXHAUSTED`
- 人工禁用：进入 `DISABLED`

---

## 5. 调度原则

### 5.1 v1 调度目标

`v1` 先做稳定可控的统一调度，不做跨 provider 的经济模型归一化。

### 5.2 v1 统一评分

```text
score =
  idle_score
+ success_score
- error_penalty
- rate_limit_penalty
- cooldown_penalty
```

### 5.3 为什么 v1 不做统一 quota_score

- 不同 provider 的计费模型差异过大
- Cookie / session 类凭证没有统一余额概念
- 插件规范要求计费逻辑私有化
- 先交付稳定调度比先做统一成本模型更重要

### 5.4 model 维度处理

- 上游可以传入 `model`
- `KeyFlow` 需要把 `model` 传给插件进行可用性判断
- 若本地已有 `supported_models`，可作为辅助过滤
- `KeyFlow` 不负责替上游改选模型

---

## 6. Redis 与 PostgreSQL 设计

### 6.1 Redis 职责

- 保存 provider 下候选 key 的调度集合
- 承担高并发分配路径
- 使用 Lua 实现原子分配

### 6.2 PostgreSQL 职责

- 持久化账户记录
- 维护正式状态
- 支撑管理接口查询
- 保存支持模型、使用计数、冷却时间等元数据

### 6.3 原子分配要求

Lua 脚本必须至少保证：

1. 只在候选集合内选择 key
2. 校验当前 key 仍可分配
3. 写入本次占用信息
4. 避免并发下同一时刻重复分配同一个 key

---

## 7. 接口设计

### 7.1 内部接口

```http
POST /api/internal/allocate-key
POST /api/internal/allocate-by-model
POST /api/internal/report-error
POST /api/internal/report-success
```

### 7.2 allocate-key 请求

```json
{
  "provider": "openai",
  "model": "gpt-4o"
}
```

### 7.3 allocate-key 响应

```json
{
  "key_id": "xxx",
  "credential": {
    "api_key": "xxx"
  }
}
```

### 7.4 allocate-by-model 请求

```json
{
  "model": "gpt-4o"
}
```

说明：

- 第二条链路只传模型名
- 账户池会在多个 provider 中筛选支持该模型且当前可用的 key
- 再按统一评分选择得分最高的 key

### 7.5 allocate-by-model 响应

```json
{
  "key_id": "xxx",
  "provider": "openrouter",
  "credential": {
    "api_key": "xxx"
  }
}
```

说明：

- 与 `allocate-key` 不同，第二条链路需要额外返回 `provider`
- 这样上游可以知道当前拿到的凭证属于哪个供应商

### 7.6 管理接口

```text
POST   /api/providers/{provider}/keys
GET    /api/providers/{provider}/keys
PUT    /api/keys/{id}
DELETE /api/keys/{id}
```

### 7.7 安全要求

内部接口通过：

```text
X-Internal-Key
```

进行服务间鉴权。

---

## 8. 插件系统职责

### 8.1 插件定位

插件是 `provider adapter`，不是账户池主存储。

### 8.2 核心负责

- 存储账户
- 查询账户池
- 决定正式状态
- 执行调度

### 8.3 插件负责

- 拉取支持模型
- 判断凭证当前是否可用
- 处理 provider 特有认证/余额/套餐/价格逻辑
- 提供安全的管理端说明信息

### 8.4 插件不负责

- 替代核心数据库保存全部账户
- 成为主状态机真相源
- 直接决定系统正式状态字段

## 9. 后台任务

### 9.1 v1 当前交付形态

- **进程模型**：`v1` 使用**单镜像双运行时**；API 入口为 `uvicorn main:app --app-dir src`，worker 入口为 `python src/worker_main.py`。
- **cooldown 恢复与刷新**：由 sidecar worker 周期性执行 `recover_cooldowns` 与 `refresh_keys`；API `lifespan` 不再自启后台循环。
- **部署单元**：API 与 worker 视为**同一个整体部署单元**，共享 PostgreSQL + Redis 真相源。
- 基础健康检查（`/health`）

### 9.2 v1 可选（未来）

- quota / balance 同步类后台能力（若独立进程化，需另立入口与部署说明）

约束：

- 如果保留在 `v1`，必须有真实逻辑
- 如果无法完成，应明确移出 `v1` 验收项

---

## 10. 部署要求

### 10.1 Docker Compose

本地部署至少包含：

```yaml
services:
  api:
  worker:
  redis:
  postgres:
```

说明：本地 Compose 以 `keyflow-api + keyflow-worker + redis + postgres` 表达同一 stack；worker 不是独立业务服务，而是同一部署单元里的后台角色。

### 10.2 K8s 兼容

- 目标形态为 **1 Pod : 2 containers**（API + worker）
- 不拆成两个彼此独立漂移的 Deployment
- 环境变量注入
- `/health` 探针

---

## 11. 与上游系统的交互

标准流程：

```text
1. Model-Forward 请求 `allocate-key` 或 `allocate-by-model`
2. KeyFlow 返回一个可用凭证；若走第二条链路，同时返回对应 provider
3. Model-Forward 调用真实 provider
4. 成功 -> report-success
5. 失败 -> report-error
6. 若需 fallback，由上游自行决定
```

---

## 14. 总结

`KeyFlow` 不是一个简单的 key 管理工具，而是任务执行链路中的资源调度组件。

统一原则如下：

```text
账户归核心，状态归核心，调度归核心；
供应商差异归插件，可用性判断归插件；
v1 先做稳定调度，不做统一额度经济模型。
```
