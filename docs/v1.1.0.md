# KeyFlow v1.1.0 阶段文档

本文档面向上游项目与上游网关的 AI，重点提供两类信息：

- 项目当前架构图与核心调用关系
- 所有 HTTP 路由接口的输入输出示例，包含成功与失败场景

说明：

- 文档中的接口路径基于默认配置 `API_PREFIX=/api`
- 除 `GET /health` 外，其余接口都需要请求头 `X-Internal-Key`
- 示例中的 `key_id`、凭据、时间字段均为示例值

## 1. 项目架构图

### 1.1 总体架构图

```text
+-------------------------------+
| 上游网关 / 上游业务系统       |
| - 申请可用 key                |
| - 上报成功 / 失败             |
| - 管理 provider/key           |
+---------------+---------------+
                |
                | HTTP / JSON
                v
+-----------------------------------------------+
| KeyFlow API (FastAPI)                         |
|-----------------------------------------------|
| 路由层                                         |
| - /health                                     |
| - /api/internal/*                             |
| - /api/providers/*                            |
| - /api/keys/*                                 |
|-----------------------------------------------|
| 应用服务层                                     |
| - KeyService                                  |
|-----------------------------------------------|
| 领域能力                                       |
| - KeyScheduler                                |
| - KeyScorer                                   |
| - KeyStateMachine                             |
+---------+----------------------+--------------+
          |                      |
          |                      |
          v                      v
+---------------------+   +----------------------+
| PostgreSQL          |   | Redis                |
| - key 元数据        |   | - 候选 key 排序集    |
| - 状态/模型/配额    |   | - 分配租约            |
| - 冷却时间          |   | - Lua 原子分配        |
+---------------------+   +----------------------+
          ^
          |
          | 读取/更新 key 状态
          |
+---------+--------------------------------------+
| KeyFlow Worker                                |
| - recover_cooldowns                           |
| - refresh_keys                                |
+---------+--------------------------------------+
          |
          | 调用 provider plugin
          v
+-----------------------------------------------+
| Provider Plugins                              |
| - OpenAI                                      |
| - Anthropic                                   |
| - Gemini                                      |
| - OpenRouter                                  |
| - GeminiWebProxy                              |
|-----------------------------------------------|
| 能力：                                         |
| - fetch_models                                |
| - is_credential_available                     |
| - mark_success / mark_error                   |
| - explain_credential                          |
+-----------------------------------------------+
```

### 1.2 核心分配流程图

```text
上游系统
  |
  | 1. POST /api/internal/allocate-key
  v
KeyFlow API
  |
  | 2. KeyService 查询 PostgreSQL 中 provider 下的 key
  | 3. KeyScheduler + KeyScorer 对候选 key 排序
  | 4. Redis + Lua 原子分配一个可用 key，并加短租约
  v
返回 key_id + credential
  |
  | 5. 上游使用该 key 调用模型供应商
  |
  | 6a. 成功 -> POST /api/internal/report-success
  | 6b. 失败 -> POST /api/internal/report-error
  v
KeyFlow 更新 PostgreSQL / Redis / plugin 内部状态
```

### 1.3 Worker 刷新流程图

```text
KeyFlow Worker
  |
  | 定时循环
  +--> recover_cooldowns
  |     - 找出冷却到期 key
  |     - 恢复为可分配状态
  |
  +--> refresh_keys
        - 调用 provider plugin
        - 刷新支持模型 / 可用性 / 缓存状态
```

## 2. 对上游最重要的接口约定

### 2.1 统一请求头

除 `GET /health` 外，其余接口都需要：

```http
X-Internal-Key: your-internal-key
Content-Type: application/json
```

### 2.2 统一错误格式

当前项目的错误响应主体比较简单，统一形态通常为：

```json
{
  "detail": "error_code"
}
```

常见错误值：

- `invalid internal key`
- `no_available_key`
- `key_not_found`
- `provider_not_found`
- `provider_not_ready`
- `duplicate_credential`

### 2.3 关键状态值

`status` 字段可能出现：

- `available`
- `rate_limited`
- `cooldown`
- `disabled`
- `exhausted`

## 3.2 按 provider 分配 key

### POST `/api/internal/allocate-key`

用途：在指定 `provider` 下分配一个当前可用的 key；可附带 `model` 进行模型过滤。

请求体示例：

```json
{
  "provider": "openai",
  "model": "gpt-4o"
}
```

成功响应示例 `200`：

```json
{
  "key_id": "key-1",
  "credential": {
    "api_key": "sk-test"
  }
}
```

失败响应示例 `401`：

```json
{
  "detail": "invalid internal key"
}
```

失败响应示例 `404`：

```json
{
  "detail": "no_available_key"
}
```

失败响应示例 `422`：

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "provider"],
      "msg": "Field required",
      "input": {
        "model": "gpt-4o"
      }
    }
  ]
}
```

## 4. 给上游网关 AI 的接入建议

如果上游网关要基于该文档自动编写接入代码，建议默认遵循以下规则：

1. 先调用 `POST /api/internal/allocate-key` 或 `POST /api/internal/allocate-by-model` 获取凭据。
2. 使用返回的 `credential` 调用真实 provider。
3. 调用成功后必须回调 `POST /api/internal/report-success`。
4. 调用失败后必须回调 `POST /api/internal/report-error`。
5. 对于 `401`，按鉴权配置错误处理。
6. 对于 `404 no_available_key`，按“当前无可用账户”处理，而不是直接重试风暴。
7. 对于管理接口，默认都要带 `X-Internal-Key`。
